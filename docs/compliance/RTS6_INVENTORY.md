# Compliance control inventory: UK RTS 6, MAR 7A, PRA SS5/18 and the US and EU flow rules

This inventory maps each requirement on an investment firm engaged in algorithmic trading to what this repository has for it: code that shows the idea in simulation, a document, nothing, or a reason the requirement does not apply. It uses the layout a firm would use for the inventory behind its annual self-assessment. This project is not a regulated firm, has no live connectivity, and does not claim compliance with any of these rules. Nothing here is legal advice.

## How to read a row

- **illustrated in simulation**: code exists and a test exercises it against the in-process simulators; the link names the code or the test. It shows how the control could work. It has not been validated against a real venue, real staff or real load, and nobody operates it.
- **document only**: a procedure, template or design exists as text; no code is involved, or the code that would carry it out is not run.
- **absent**: nothing in the repository meets the requirement, or the control described in an earlier version of this page does not operate.
- **out of scope**: the requirement does not apply to this platform, with the reason.

Statuses were revised on 2026-11-23 after the review of that date (docs/reviews/REVIEW_2026-11-23.md, findings E2 and E9). The earlier scale (implemented, evidenced, planned) rated some rows on review and change-management controls that do not operate: there is one person and no independent reviewer (CONTRIBUTING.md). Those rows are downgraded below. Rows 5, 10, 12, 14 and 17 were brought up to 1.2.0 on 2026-11-23 on the same scale: 1.2.0 adds an opt-in v2 desk profile with four venue sessions, a wired-desk latency benchmark and a router benchmark; the default desk is unchanged.

Sources (checked 2026-10-31): Commission Delegated Regulation (EU) 2017/589 as it forms part of UK law ("UK RTS 6"), [legislation.gov.uk/eur/2017/589](https://www.legislation.gov.uk/eur/2017/589/contents), whose article titles and Annex II layout are used below; FCA Handbook MAR 7A (algorithmic trading); PRA Supervisory Statement SS5/18 "Algorithmic trading" (June 2018); CFTC regulations 17 CFR 1.73 and Part 43, and Part 37 for swap execution facilities; UK MiFIR Articles 10, 11 and 21 and the onshored RTS 2 for post-trade transparency. legislation.gov.uk marks UK RTS 6 as revoked by the Financial Services and Markets Act 2023 (Schedule 1, Part 3) with effect from a date set by commencement regulations, as the FCA restates retained EU law in its Handbook; the obligations below apply until then and are expected to carry into the FCA rules. The owner should confirm the commencement position before relying on any row.

## UK RTS 6, article by article

| Article | Requirement in brief | Status | Control and evidence |
|---|---|---|---|
| 1 General organisational requirements | Governance and accountability for algorithmic trading, clear lines of responsibility, documented processes | document only | One person holds every role. The runbooks name desk roles on paper ([docs/runbooks/README.md](../runbooks/README.md)); how work is actually done is in [CONTRIBUTING.md](../../CONTRIBUTING.md) and [docs/AI_USE_POLICY.md](../AI_USE_POLICY.md). No separation of responsibilities exists |
| 2 Role of the compliance function | Compliance understands the algorithms and has kill-switch access | document only | There is no compliance function. The runbooks describe escalation to one ([docs/runbooks/](../runbooks/README.md)); kill-switch access is whoever holds the control token: since 1.1.0 `POST /control/kill` refuses every caller when no token is configured ([OpsHttpServer](../../rates-ops/src/main/java/io/ratesalgo/ops/http/OpsHttpServer.java), review L12) |
| 3 Staffing | Sufficient staff with the knowledge to run and supervise the algorithms | out of scope | A one-person open project; the separation of roles is kept on paper in the runbooks so the procedures read as they would on a desk |
| 4 IT outsourcing and procurement | Firm remains responsible for outsourced components | out of scope | No outsourced trading components. Third-party Java libraries are pinned in `pom.xml`; Python dependencies are pinned by a constraints file, `research/requirements-lock.txt`, without hashes; Actions are pinned by commit SHA ([SECURITY.md](../../SECURITY.md)); there is no independent review of any of them |
| 5 General methodology | Algorithms tested before deployment and on material change, in a methodology the firm documents | illustrated in simulation | Required CI checks run on every pull request ([.github/workflows/ci.yml](../../.github/workflows/ci.yml)); deterministic replay is the test method ([docs/ARCHITECTURE.md](../ARCHITECTURE.md), Testing strategy). The tests were written by the same assistant sessions as the code and nobody validates them independently ([docs/AI_USE_POLICY.md](../AI_USE_POLICY.md)); there is no deployment to test before. Since 1.2.0 the second versions of the simulator, pricing, strategy and router are built behind an opt-in desk profile and are not the default; a change of default waits for a pre-registered simulator run, and the first such registration (`research/prereg/R5-FAM-001.yaml`) is unsigned and has not run. The ladder router was benchmarked once against declared alternatives in its own simulator before any adoption, and the check declared before that run failed against one of them; the failure is recorded, not tuned away ([docs/research/ROUTER_BENCHMARK.md](../research/ROUTER_BENCHMARK.md), `RouterBenchmarkTest`) |
| 6 Conformance testing | Conformance with each venue's systems before trading and after material change | illustrated in simulation | P2 venue simulators and a FIX 4.4 certification suite: `CertSuiteTest` runs 16 scripts across the D2C RFQ, D2D CLOB and SEF simulators (`rates-venues`), with the codec tests in `rates-fix`; listed as the Conformance row of the testing strategy in [docs/ARCHITECTURE.md](../ARCHITECTURE.md). Conformance with a real venue is a test against that venue and is not covered |
| 7 Testing environments | A testing environment separate from production | illustrated in simulation | There is no production. The simulated environment ([deploy/compose.yaml](../../deploy/compose.yaml)) and the process-mode rehearsal ([deploy/rehearsal.py](../../deploy/rehearsal.py), job `rehearsal` in [ops.yml](../../.github/workflows/ops.yml)); no path from either to a live venue |
| 8 Controlled deployment of algorithms | Limits on instruments, size and messages at first deployment | illustrated in simulation | Per-process instrument list and limits in versioned configuration validated at start ([deploy/config/schema/process-config.schema.json](../../deploy/config/schema/process-config.schema.json), `ConfigValidationTest`); blue/green switch ([deploy/bluegreen.sh](../../deploy/bluegreen.sh)), which since 1.1.0 records the new colour as active only after the old colour's kill is confirmed, unless an operator overrides it with `RATES_OLD_COLOUR_CONFIRMED_DOWN=1`, which the state line records (review E8, `BlueGreenScriptTest`). The wired desk's default limits are sized so that the smoke day never breaches them (`DeskSettings.limits()`, [DeskSettings](../../rates-app/src/main/java/io/ratesalgo/app/loop/DeskSettings.java)) |
| 9 Annual self-assessment and validation | Annual self-assessment against Annex I criteria and a validation report approved by senior management | document only | Never carried out. Template: [SELF_ASSESSMENT_TEMPLATE.md](SELF_ASSESSMENT_TEMPLATE.md), including the senior-management validation report; this inventory is its main input |
| 10 Stress testing | Systems withstand twice the highest message and trade volume of the previous six months | illustrated in simulation (harness only; no stress result is recorded) | `StressReplayer` replays a journal with its busiest window at twice the recorded rate and records acceptance and latency ([StressReplayer](../../rates-ops/src/main/java/io/ratesalgo/ops/stress/StressReplayer.java), `StressReplayerTest`); bound to the P2 loop's ring buffer by the coordinator; results to be recorded in docs/BENCHMARKS.md under DR-005. Since 1.2.0 a latency benchmark runs the real trading process over loopback FIX at 1,000 QuoteRequests a second ([WiredDeskBenchmark](../../rates-bench/src/main/java/io/ratesalgo/bench/wired/WiredDeskBenchmark.java), [docs/BENCHMARKS.md](../BENCHMARKS.md)); it measures latency at a fixed load on a loaded laptop, not capacity at twice a recorded peak, so it is not a stress result either |
| 11 Management of material changes | Material changes tested and approved before deployment | absent | Changes are tested by the required CI checks and recorded in git, decision records ([DECISIONS.md](../../DECISIONS.md)) and versioned configuration ([deploy/config/](../../deploy/config/trading-blue.yaml)). Approval by a second person does not happen: the `main` ruleset requires 0 approvals and no pull request has had one ([CONTRIBUTING.md](../../CONTRIBUTING.md)) |
| 12 Kill functionality | Cancel all unexecuted orders and quotes immediately, for all or some algorithms, traders or venues | illustrated in simulation | `POST /control/kill` (token required) has two paths since 1.1.0. A halt flag is read by each venue session's gateway thread, which stops sending anything from the loop, cancels every quote and order in its own record of live business, repeats unanswered cancels and then logs out so the venue cancels on disconnect; this path needs neither a live loop nor ring space. The `KillSwitch` message (template 31, scope id, requester's party id) is still journaled through the loop so replay reproduces the pull. The endpoint answers 200 only when the venues confirmed the withdrawal and 503 with the reason otherwise. A supervisor thread halts the process when a loop or the gateway thread dies or stalls (review L1, L2; [API_SPEC.md](../../API_SPEC.md) Section 18.9; DR-RV-S01 to S03; `VenueSessionHaltTest`, `SupervisorTest`, `ControlEndpointTest`, `OpsProcessTest.killSwitchPullsEveryQuoteAndIsJournaled`); exercised in CI by the rehearsal; alert `QuotesLiveAfterKill` ([alerts.yml](../../deploy/prometheus/alerts.yml)). Since 1.2.0, on the opt-in v2 desk profile, the halt, the kill, the supervisor and the undelivered-message halt cover all four venue sessions (D2C, two Treasury CLOBs, futures), each on its own thread; the kill is confirmed only when all four report nothing of ours working (`TradingProcessV2Test.aSteppedDayIsKilledOnEveryVenueReconcilesReplaysAndRepeatsFrameForFrame`; [SupervisorV2Test](../../rates-app/src/test/java/io/ratesalgo/app/SupervisorV2Test.java) with a dead loop, a stuck futures session and venues that stop answering; `python deploy/rehearsal.py --mode process --profile v2`; [v2-profile.md](../runbooks/v2-profile.md)). Scope is the whole process; a kill for one algorithm, trader or venue is not offered, and a halt is final until restart |
| 13 Automated surveillance to detect market manipulation | Surveillance of orders and transactions, with alerts reviewed | illustrated in simulation (detectors only; nobody reviews the alerts) | `SurveillanceDetector` with `QuoteStuffingDetector` and `SelfTradeDetector` over journal frames (`SurveillanceTest`); alerts written daily by `EodReportMain`; review step in [end-of-day.md](../runbooks/end-of-day.md). A desk would add a vendor surveillance system fed from the same journal |
| 14 Business continuity arrangements | Continuity plan, tested, including the kill function and recovery | illustrated in simulation (process restart on its journals and post-trade restart); standby absent | Post-trade restart procedure: replay, venue status reconciliation, quoting only after ([RestartProcedure](../../rates-posttrade/src/main/java/io/ratesalgo/posttrade/recovery/RestartProcedure.java), `RestartProcedureTest`). Since 1.1.0 the trading process restarts on its own journals: torn-tail repair, state rebuilt by replay, refusal on a broken chain, FIX sequence resume and order reconciliation before the CLOB is used again ([restart.md](../runbooks/restart.md), `RestartRecoveryTest`, review L6). The sequence store survives a process crash, not a power loss. Since 1.2.0 a process on the opt-in v2 profile restarts on a crash image with sequence numbers resumed on its four sessions ([TradingProcessV2Test](../../rates-app/src/test/java/io/ratesalgo/app/TradingProcessV2Test.java)); its simulated market restarts without the impact of the desk's earlier trades. Warm standby over Aeron is designed, not built ([warm-standby-design.md](../runbooks/warm-standby-design.md), [standby-takeover.md](../runbooks/standby-takeover.md)) |
| 15 Pre-trade controls on order entry | Price collars, maximum order value and volume, maximum messages, before an order leaves | illustrated in simulation | `RiskEngine` checks price collar, fat finger, maximum order size, position, PV01, daily loss and quote, order and message rates (`rates-risk`, `RiskEngineTest`; `LimitKind` in [API_SPEC.md](../../API_SPEC.md) Section 2). The wired desk's default (back-test) preset sets no price collar or fat-finger quantity, keeps the 10% fat-finger price check, and sizes its other limits so the smoke day never breaches them. Since 1.1.0 there are per-RFQ and per-client DV01 limits and a desk-sized preset with a 10 bp collar and a 200mm fat-finger quantity, neither on by default ([DeskSettings](../../rates-app/src/main/java/io/ratesalgo/app/loop/DeskSettings.java), review Q9, DR-RV-Q04, DR-RV-Q05). Risk-reducing orders now pass the pillar, net and gross checks (DR-RV-Q02); deployment limits are in [deploy/config](../../deploy/config/trading-blue.yaml) |
| 16 Real-time monitoring | Real-time monitoring of algorithmic activity with alerts, by staff who can act | illustrated in simulation (no staff watch it) | Prometheus metrics ([MetricNames](../../rates-ops/src/main/java/io/ratesalgo/ops/metrics/MetricNames.java)), dashboard ([rates-trading.json](../../deploy/grafana/dashboards/rates-trading.json)) and alert rules with runbook links, linted in CI (`tools/lint_dashboards.py`) |
| 17 Post-trade controls | Continuous post-trade assessment, reconciliation of trading logs with venue, broker and clearing records | illustrated in simulation (after the run, not continuous) | Position keeper, which reads the journals after the run ([PositionKeeper](../../rates-posttrade/src/main/java/io/ratesalgo/posttrade/position/PositionKeeper.java)); daily reconciliation against drop copies, clearing and books and records with classified breaks; zero unexplained breaks on the synthetic day (`ChaosDayTest`); [reconciliation-break.md](../runbooks/reconciliation-break.md). Since 1.2.0 the v2 profile reconciles with each of its four venues in venue units ([V2Reconciliation](../../rates-app/src/main/java/io/ratesalgo/app/sim/V2Reconciliation.java)); the v2 smoke day reconciled 72 of 72 trades |
| 18 Security and limits to access | Access to systems restricted; security incidents handled | illustrated in simulation (part) | Since 1.1.0 every control path needs the token, compared in constant time; with no token the control endpoints refuse everyone and a non-loopback bind refuses to start; the shipped configs bind 127.0.0.1. With `http.tls` the endpoint is HTTPS, and a non-loopback bind needs both the token and TLS (`HttpsEndpointTest`). FIX runs over TLS 1.3 with Logon credentials compared in constant time; plain FIX is loopback only (`TcpInitiatorTlsTest`, `VenueSecurityTest`). Secrets come from environment variables or files only ([certificate-rotation.md](../runbooks/certificate-rotation.md)). Compose publishes ports on 127.0.0.1 only; containers run as a non-root user ([deploy/trading/Dockerfile](../../deploy/trading/Dockerfile)); [SECURITY.md](../../SECURITY.md) |
| 19 to 23 Direct electronic access | Obligations on firms that provide DEA to clients | out of scope | The platform trades as principal and offers no DEA |
| 24 to 27 General clearing members | Obligations on firms acting as general clearing members | out of scope | The platform is a clearing client, not a clearing member; its clearing state machine models the client side ([ClearingLifecycle](../../rates-posttrade/src/main/java/io/ratesalgo/posttrade/clearing/ClearingLifecycle.java)) |
| 28 and Annex II Content and format of order records | Records of every order and decision in the Annex II layout, kept for five years | illustrated in simulation | `OrderRecord` carries the Annex II Table 2 and Table 3 fields that apply ([API_SPEC.md](../../API_SPEC.md) Section 17.4); `RecordArchive` keeps them by date for five to seven years; every record retrievable by venue order id (`RecordRetentionTest`) |
| 29 Entry into force | Not a control | out of scope | No obligation |
| Annex I Self-assessment criteria | Nature, scale and complexity of the algorithmic trading | document only | A section per criterion, not filled in, in [SELF_ASSESSMENT_TEMPLATE.md](SELF_ASSESSMENT_TEMPLATE.md) |

The controls above are drawn by group (pre-trade, real-time monitoring, kill, post-trade, surveillance and stress, change management) in [RTS 6 control map](../site/pages/diagrams.md#rts-6-control-map).

## FCA MAR 7A and PRA SS5/18

| Reference | Requirement in brief | Status | Control and evidence |
|---|---|---|---|
| MAR 7A.3 systems and risk controls | Resilient systems, thresholds and limits, prevention of erroneous orders, testing | illustrated in simulation | As RTS 6 Articles 5 to 18 above |
| MAR 7A.3 notification | Notify the FCA (and venues) that the firm engages in algorithmic trading | out of scope | Not a regulated firm; a desk notifies before go-live |
| MAR 7A.3 records | Keep records the FCA can request of algorithms, parameters and limits | document only | Algorithm inventory, seven rows for the simulated environment (three of them opt-in since 1.2.0), none deployed ([ALGORITHM_INVENTORY_TEMPLATE.md](ALGORITHM_INVENTORY_TEMPLATE.md)); configuration under version control; the journal |
| MAR 7A.3 market making | Market-making agreements with venues where a strategy meets the market-making definition | out of scope | Simulated venues only; the RFQ and CLOB strategies would be assessed against the definition before go-live |
| SS5/18 governance | Senior management accountability, an algorithm approval process, a named owner per algorithm | absent | One person; the algorithm inventory names "owner" as both owner and approver of every algorithm; pull requests are merged without approval ([CONTRIBUTING.md](../../CONTRIBUTING.md)) |
| SS5/18 algorithm inventory | A complete, current inventory with risk tiering | document only (template) | [ALGORITHM_INVENTORY_TEMPLATE.md](ALGORITHM_INVENTORY_TEMPLATE.md) |
| SS5/18 testing and approval | Independent testing proportionate to risk; approval before deployment | absent | Testing is CI, replay determinism, golden tests (P1) and back-test pre-registration (P5), written by the same sessions as the code; nothing is tested or approved independently ([docs/AI_USE_POLICY.md](../AI_USE_POLICY.md)) |
| SS5/18 risk controls | Pre-trade and post-trade controls, kill switch, limits owned by risk | illustrated in simulation | Rows 12, 15 and 17. No risk function owns the limits ([DeskSettings](../../rates-app/src/main/java/io/ratesalgo/app/loop/DeskSettings.java)) |
| SS5/18 change management | Change controlled, recorded and reversible | document only | Changes are recorded in git and decision records ([DECISIONS.md](../../DECISIONS.md)) and can be reverted in git; no second person controls them; the blue/green switch is a script ([deploy/bluegreen.sh](../../deploy/bluegreen.sh)) |

## US swap flow: CFTC and SEF rules

| Reference | Requirement in brief | Status | Control and evidence |
|---|---|---|---|
| CFTC Rule 1.73 | A clearing member screens orders against risk-based limits before execution (pre-execution credit check), for orders on a SEF or DCM | absent (simulator backstop only) | No pre-execution credit check is built; the clearing simulator rejects past the limit as a backstop and the rejection voids the trade (`ClearingLifecyclePropertiesTest.simulatorAcceptsWithinLimitAndRejectsBeyondIt`) |
| CFTC Part 37 SEF execution | Trades in made-available-to-trade swaps executed on a SEF by RFQ to at least three or by order book | illustrated in simulation (SEF not connected to the trading process) | `SefSimulator` in `rates-venues` enforces `SefConfig.requiredMinDealers` on Required Transactions below block size; the RFQ message carries `dealerCount` ([API_SPEC.md](../../API_SPEC.md) Section 2) |
| CFTC Part 37 and 39 void ab initio | A SEF trade rejected for clearing is void | illustrated in simulation | REJECTED is terminal in the clearing lifecycle and the caller busts the trade with reason ClearingRejected; the reconciliation explains the resulting break (`KeeperFacts`, explanation CLEARING_REJECTED) |
| CFTC Part 43 real-time public reporting | Swap transactions publicly disseminated as soon as technologically practicable, with block and cap rules | absent | The reporting party is the SEF for on-SEF trades; the platform's obligation would be to supply the fields, which the order record and trade key carry. A Part 43 message to an SDR is not built |
| CFTC Part 45 regulatory reporting | Creation and continuation data to an SDR | out of scope | Reporting counterparty duties of a swap dealer; not modelled in a simulated environment |

| UK MiFIR Art 21 and RTS 2 | Investment firms make public the price, volume and time of OTC trades in bonds and derivatives through an APA | absent | Fields available from the order record (instrument identifier, price, notation, quantity, time to the nanosecond); no APA publication message is built |
